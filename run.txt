The default is the normal 25-second simulation with corrected eating and reproduction.
Choose the eating implementation in the normal simulation:
java -cp out Main --eating=safe
java -cp out Main --eating=race

Reproduce the eating issue reliably using two real Cell threads and one food unit:
java -cp out Main --demo=eating --eating=race
Expected: 2 successful meals, -1 food remaining, food limit VIOLATED.

Run the corrected version of the same scenario:
java -cp out Main --demo=eating --eating=safe
Expected: 1 successful meal, 0 food remaining, food limit PASS.

The faulty implementation checks units.get() > 0, then decrements separately.
Both operations individually use AtomicInteger, but their combination is not atomic.
Two cells can both see the last food unit before either decrements it.
The fix combines the availability check and decrement using getAndUpdate.
This is a check-then-act race / data consistency issue in the eating system.

--demo=eating enables scheduling hooks only for the first two attempts. In race
mode both cells wait at a barrier after checking availability, before decrementing.
In safe mode they wait before the complete atomic consume operation. The barrier
does not change the food count or meal results; it selects an overlapping schedule.
Long fullness/starvation times prevent extra meals or death deposits during the demo.
The demo waits for both attempts, stops and joins both cells, then prints the result.
Normal simulation runs have no scheduling barriers; their race may or may not appear.
The mating tick remainder wait and stop/join-before-summary behavior are preserved.

Reproduction issue (category 2: deadlock)
---------------------------------------
java -cp out Main --demo=reproduction --reproduction=deadlock
Expected final evidence (cell log order can vary):
JVM-confirmed parent deadlock: true
Cell-1-sexual waits for Cell-2-sexual; Cell-2-sexual waits for Cell-1-sexual
Committed parents: 0
Children created: 0
All cell threads stopped: true

java -cp out Main --demo=reproduction --reproduction=safe
Expected final evidence:
JVM-confirmed parent deadlock: false
Committed parents: 2
Children created: 1
All cell threads stopped: true

Both switches are independent; safe reproduction is the default:
java -cp out Main --eating=race --reproduction=safe
java -cp out Main --eating=safe --reproduction=deadlock
These run the normal 25-second simulation. Without scheduling hooks the faulty
lock ordering might or might not deadlock. Shutdown interrupts and joins cells,
including cells blocked acquiring reproductive locks. Choose only one demo.
The eating demo retains its own isolated setup and existing behavior.

Motivation: committing a sexual mating updates both parents' reproductive records
(completed mating count and last partner) together and claims a single offspring.
Both parents process the exchanged match. A shared per-match token, selected by
unique exchange tickets, makes the commit idempotent even if a parent is delayed.
The two record locks protect both the joint update and the offspring claim.
The faulty version reasonably starts with its own record and then its partner's.
Opposite callers can each hold their own lock and wait indefinitely for the other.
The correction acquires the same two locks in ascending cell-ID order. The commit
and birth behavior are otherwise identical. This is a circular-wait deadlock.

The demo uses real sexual Cell threads and 20 food units: each actually eats ten
meals, with one full tick between meals. It aligns the parents before exchange.
Only faulty mode then aligns them after each has acquired its first record lock.
The hook changes no locks, food, records, or birth results. After the hook releases,
the actual second lock acquisitions cause the cycle. ThreadMXBean must identify
both parents as deadlocked with each owning the lock the other needs. A deadline
alone never counts as a reproduced deadlock. Safe mode must commit both parents
and actually spawn exactly one child. All result summaries follow shutdown/join.

Locks use lockInterruptibly: the cycle persists until external cancellation, but
interrupting both parents releases their held locks through finally blocks. This
allows bounded in-process demos without leaving daemon cells behind. Demo waits
have explicit deadlines; coordination or observation failure raises an error,
rather than claiming a concurrency failure. Successful mating still waits out
the remainder of its tick. No hooks are installed in normal simulations.
